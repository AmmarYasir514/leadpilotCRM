# LeadPilot CRM — Consolidated QA report

**Date:** 21 November 2026  
**Assessment:** Functional coverage is partial; not ready to claim 100% completion or production readiness.  
**Method:** Isolated automated tests, production frontend build, authenticated desktop navigation smoke test, targeted source review, and synthetic PDF stress test. No customer data or external services were modified for QA.

## Executive summary

The application builds successfully, its existing backend automated suite passes, and the main desktop screens opened during the browser navigation check. These results are useful, but they do not prove that every screen or integration works end to end. The most important remaining product gap is that the official Upwork live conversation and proposal previews are not yet fully saved and connected to CRM leads and follow-up cycles. The inbox currently displays the latest available message, rather than full history. A draft-loss issue was identified in its source code. The single-page report becomes two pages with a larger target list.

## Findings, ordered by priority

### 1. Official Upwork data is not fully synchronized with CRM — High

**Evidence:** The live conversations interface explicitly says its results are temporary and not linked to saved CRM leads or sales cycles; the proposal interface says its results are temporary. Profile sync saves a private snapshot. Job-search results are also explicitly tested as not persisted. See `resources/js/UpworkLiveConversations.tsx`, `resources/js/UpworkLiveRecords.tsx` and `tests/Feature/UpworkMcpTest.php`.

**Impact:** Connecting Upwork does not yet deliver the requested complete onboarding and synchronization of jobs, proposals, conversations, leads and follow-up timing. A live preview should not be treated as a saved CRM record. The existing extension cannot be declared unnecessary based on this QA. Any future use alongside official integration needs Upwork-policy review.

**Next:** Implement supported official data flows, reliable identifiers and duplicate handling; connect saved data to leads and follow-ups; test with a real account and records, while respecting available provider permissions.

### 2. Inbox is a last-message preview, not full chat history — High product gap

**Evidence:** `resources/js/ChatInbox.tsx` labels live mode “latest message only” and passes the last available message to the AI writer. It does not load an entire conversation into the displayed inbox.

**Impact:** Users cannot review full conversations in LeadPilot or expect AI to understand messages that were not supplied to it. Sender, elapsed-time and follow-up decisions require reliable source data and complete integration before they can be trusted.

**Next:** Determine the history and sender details the official connection actually supplies, display availability clearly, and validate follow-up decisions against the latest activity. Do not infer timestamps or senders when unavailable.

### 3. Unsent inbox text can be cleared by clicking the selected chat — Medium bug

**Evidence:** In `resources/js/ChatInbox.tsx`, the selected-chat click handler only asks for confirmation when changing to a different chat, but calls `setTyped('')` even when the current chat is clicked again.

**How to reproduce:** Open Chats, type an unsent message, then click that same selected conversation again. Source logic indicates the message is cleared without confirmation. This scenario was identified by code review and was not re-run interactively after the session ended.

**Next:** Preserve the draft when selecting the active chat and add an interaction regression test.

### 4. Attachments and follow-up delivery have incomplete end-to-end verification — High product gap

**Evidence:** The inbox attachment control links to Upwork; it is not an in-CRM attachment upload. The inbox has a direct send path with a confirmation, and its tests simulate Upwork responses. Those tests do not verify an actual delivery. Marking a follow-up as sent is not evidence that an external message was delivered.

**Next:** Confirm official provider support for sending and attachments, clearly label unsupported actions, and separately test confirmed send, failure/unknown delivery and follow-up completion with an authorized test account. Do not automatically retry an unconfirmed send.

### 5. One-page PDF is not guaranteed for larger reports — Medium presentation issue

**Evidence:** A synthetic 20-target report generated two A4 pages; text extraction found all 20 target labels. This was a data-preservation/pagination check, not a full visual inspection of every layout edge. The report template iterates over all targets in `resources/views/reports/sales-performance.blade.php`.

**Impact:** The requested one-page presentation works only within the content that fits. Large target lists overflow to additional pages. Forcing all content onto one page could make it unreadable.

**Next:** Define a readable one-page summary plus clearly labelled continuation pages or a compact target summary, then visually review short and long reports, long names and print output.

### 6. Complete real-service and responsive verification is outstanding — High QA gap

The QA session was no longer authenticated during the integration checks, so live Upwork, Google Calendar and OpenAI workflows could not be tested in this pass. Full signed-in mobile/tablet layouts, keyboard navigation, screen-reader accessibility, cross-browser behaviour, load/performance and production deployment were not tested. Voice was reported working by the user in an earlier conversation but was not retested here.

**Next:** Sign in locally, share the LeadPilot tab, and use a safe test account and controlled sample records. Check responsive screens and keyboard access; then validate integrations and delivery only with explicit permission for external actions.

## Recommended completion order

1. Fix the unsent draft loss; add an interaction regression test.
2. Complete supported official Upwork imports and reliable CRM/follow-up synchronization; clarify what the provider cannot supply.
3. Complete chat history/context, delivery and attachment flows where supported; validate against a real test account without unsolicited sends.
4. Finalize readable PDF behaviour for both small and large reports.
5. Run an authenticated screen-by-screen browser pass, mobile/tablet and accessibility checks, then real-service, security and deployment checks.

**Overall:** The checks above establish a working foundation and identify concrete gaps. They do not support a claim of 100% QA completion or production readiness.
